

How to read this document: every requirement is written so a teammate can mark it pass or fail without asking the author. Priorities are **Must** (the club cannot run a competition without it), **Should** (important, can ship in a later release), **Could** (nice to have).

## 1. Functional Requirements

### 1.1 Scoring page

| ID    | Requirement (pass when...)                                                                                                                                                                                                                                 | Priority and reason                                                  |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| FR-1  | On the home screen, a user can enter an event code to open a scorecard for that event                                                                                                                                                                      | Must: core purpose of product                                        |
| FR-2  | A user can choose their name from a searchable list that shows only public display names.                                                                                                                                                                  | Must: replaces user accounts (C-5).                                  |
| FR-3  | After a name is chosen, it is remembered on that device across browser restarts and is pre-selected on the next visit. | FR-4  | The user can enter one score per arrow with a single tap, using the score values defined for that event (for example X, 10 to 1, M). Each end total and the running total update on screen. | FR-6  | If the event is not open for submissions and any grace period (FR-37) has ended, the server rejects the scorecard, the user sees a message saying submissions are closed, and the draft stays on the device.                                               | Must: brief requires admin-controlled submission windows (C-6).      |

| FR-10 | One device can hold several scorecards at once (for example own card plus those being scored for others) and the user can switch between them in 1 tap. | FR-11 | A member can view their past scorecards, grouped by event, each showing date, bow used, target type & distance, individual arrows, and total.                                                                                                              | Must: brief requires scorecard history.                              |
| FR-12 | A member can view their running average for the current League competition (if they've participated)                                                                                                                                                       | Must: brief requires averages.                                       |
| FR-13 | The current League competiton and pinshoot have a public leaderboard showing display names and scores only                                                                                                                                                 | Must: brief requires public leaderboards.                            |

### 1.4 Back-end logic

|       |                                                                                                                                                                                                                                                                                                                                                                                                                                                       |                                                                                                                     |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| ID    | Requirement (pass when...)                                                                                                                                                                                                                                                                                                                                                                                                                            | Priority and reason                                                                                                 |
| FR-31 | The server computes totals, averages and rankings from stored arrow scores using the event's configured rules. Clients never send totals that are trusted without recomputation.                                                                                                                                                                                                                                                                      | Must: prevents tampering and rule drift.                                                                            |
| FR-32 | An admin can generate teams for League competitions from the checked-in or scored members using a selected method (random, or balanced by average) and a team size, and can re-generate or manually move members.                                                                                                                                                                                                                                     | Should: brief lists team-making, but rules are undefined (OQ-9).                                                    |
| FR-33 | An admin can define pin achievements (name and threshold rule, such as a minimum total on a given round). The system awards them automatically on submission and a member can see the pins they have earned.                                                                                                                                                                                                                                          | Should: brief lists pins, but criteria are undefined (OQ-8).                                                        |
| FR-34 | The database links every member to every scorecard they submitted, across all events, so any member's full history can be listed.                                                                                                                                                                                                                                                                                                                     | Must: foundation for FR-11 and FR-12.                                                                               |
| FR-36 | A member enters a valid event code once per event per device. The server then issues an event-scoped token, stored on the device, that authorizes all later submissions for that event for the token lifetime (default 12 hours), with no code re-entry. After the grace period they are rejected.                                                                                                                                                                                                                                 | Should: a card finished in a dead zone must not be lost just because the admin closed the event.                    |

## 2. Non-Functional Requirements

### 2.1 Performance and connectivity

| ID    | Quality                        | Measure and target                                                                                                                                                                                                                                                                           | Priority and reason                                   |
| ----- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| NFR-1 | Page weight                    | First visit to the scoring page transfers at most 150 KB compressed. Measured in the browser network panel.                                                                                                                                                                                  | Must: weak cellular signal outdoors.                  |
| NFR-2 | Load time                      | Scoring page is interactive in 4 s or less on Chrome DevTools "Slow 4G" throttling with 4x CPU slowdown, median of 5 runs.                                                                                                                                                                   | Must: same reason; slow phones also expected.         |
| NFR-3 | Repeat visit                   | A repeat visit transfers 10 KB or less and is interactive within 1.5 s under the NFR-2 conditions. Static files use fingerprinted names with cache lifetime of 1 year.                                                                                                                       | Must: brief requires caching wherever possible.       |
| NFR-4 | Offline entry                  | Scorecard remains functional when internet connectivity lapses. Archer can submit once they regain connectivity                                                                                                                                                                              | Must: dead zones at the range.                        |
| NFR-5 | Entry responsiveness           | The UI reflects an arrow tap within 100 ms with no network.                                                                                                                                                                                                                                  | Must: slow entry disrupts competitions.               |
| NFR-6 | Request efficiency             | A scorecard submission is one request of 5 KB or less.                                                                                                                                                                                                                                       | Must: efficient server communication.                 |
| NFR-7 | Retry resilience               | In a simulated 30-minute network outage, 0 of 20 queued scorecards are lost. Retries use exponential backoff, and queued cards remain until they succeed or the user discards them. Queued cards authorize with the stored event token, so regenerating the event code does not strand them. | Must: scores are irreplaceable.                       |
| NFR-8 | Idempotency                    | Sending the same scorecard 10 times produces exactly 1 stored record.                                                                                                                                                                                                                        | Must: retries must not duplicate scores.              |
| NFR-9 | Leaderboard freshness and size | A submitted card appears on the leaderboard within 30 s when online. The leaderboard payload is 50 KB or less for 150 members.                                                                                                                                                               | Should: live feel at events, not critical to scoring. |

### 2.3 Security and privacy

| ID     | Quality                                                     | Measure and target                                                                                                                                                                                                                                                                                                                                                           | Priority and reason                                                                           |
| ------ | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| NFR-17 | Rate limit, member password, event code and join passphrase | After 5 failed attempts from one IP address within 15 minutes _(defaults, adjustable via FR-27)_, further attempts return HTTP 429 until the window ends. Verified by script: attempt 6 is blocked even with the correct password.                                                                                                                                           | Must: brute-force protection.                                                                 |
| NFR-18 | Rate limit, admin password                                  | Same mechanism as NFR-17 with its own counter. Defaults 5 attempts per 15 minutes.                                                                                                                                                                                                                                                                                           | Must: protects the most powerful access.                                                      |
| NFR-19 | Password storage                                            | A full dump of the database contains no plaintext or reversibly encrypted password, passphrase or admin password.                                                                                                                                                                                                                                                            | Must: limits damage from a leak.                                                              |
| NFR-20 | Real-name isolation                                         | A crawl of every public URL and API endpoint returns 0 occurrences of any stored real name (unless a user chose to make their username their real name).                                                                                                                                                                                                                     | Must: privacy promise (FR-18).                                                                |
| NFR-21 | Search-engine exclusion                                     | Every page response carries a noindex directive and robots.txt disallows all crawling. Verified with curl.                                                                                                                                                                                                                                                                   | Must: brief says the site must not appear in search.                                          |
| NFR-22 | Transport                                                   | HTTP requests redirect to HTTPS. No public page loads mixed content.                                                                                                                                                                                                                                                                                                         | Must: passwords are sent over the network.                                                    |
| NFR-23 | Write protection                                            | Submissions for an event with status Closed are rejected server-side 100% of the time once any grace period (FR-37) has ended, including requests made directly to the API without the UI.                                                                                                                                                                                   | Must: C-6 enforced on the server, not just hidden in the page.                                |
| NFR-30 | Event-code guessing, global limit                           | After 50 failed code attempts for one event across all IPs within 10 minutes (defaults, adjustable via FR-27), further code attempts for that event are refused for 10 minutes. Devices holding a valid token and member-password mode keep working. Verified by script: 60 distinct IPs each send 1 wrong code, attempt 51 is refused, and a token holder can still submit. | Should (in Event code mode): per-IP limits alone do not stop guessing spread across many IPs. |
| NFR-31 | Event-code strength and lifetime                            | Codes come from a cryptographically secure random generator and are at least 4 characters from a 31-character alphabet. A code is rejected after its event closes. Verified by a generator unit test and by trying a code from a closed event.                                                                                                                               | Must (in Event code mode): this strength is what makes a short code acceptable.               |

## 3. Constraints

These are limits fixed by the project brief or by the environment. They are not open to negotiation within this document.

| ID  | Constraint                                                                                                                                                        |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C-1 | The product will be used and managed by student volunteers with high turnover, so the app must be highly intuitive                                                |
| C-2 | Future club officers will likely have little technical knowledge. Therefore, the product must be incredibly stable to reduce chances of needing technical support |

## 4. Non-Goals

The following are deliberately out of scope for this version.

- Individual user accounts, email login, or social login.
- Public search-engine visibility or marketing pages.
- Support for multiple clubs or organizations in one deployment.
- Native iOS or Android apps. The product is a mobile web app only.
- Automatic scoring from photos of targets.
- Submitting results to external bodies such as national archery organizations.
- Guaranteeing prevention of cheating. Double scoring (FR-9) reduces it and the audit log (FR-22) records changes, but no stronger guarantee is promised.
